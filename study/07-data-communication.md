# データ・コミュニケーション解説

この文書は、WebRTCにおけるデータ通信の仕組み（データチャンネル、DCEP、SCTP）についてまとめたものです。

---

## 1. データチャンネルの概要

- 2つのピア間で最大**65,534個**のデータチャンネルを開設可能
- デフォルトは**順序保証あり**の信頼性のある配信
- UDPのように**順序なし・損失あり**に設定することも可能
- 低レイテンシー・高パフォーマンスが強み
- バックプレッシャーを測定し、ネットワークがサポートする量だけを送信できる

---

## 2. 使用プロトコル

| プロトコル | 役割 |
|-----------|------|
| **SCTP** (Stream Control Transmission Protocol) | データチャンネルの基盤トランスポート。多重化・信頼性・輻輳制御を提供 |
| **DCEP** (Data Channel Establishment Protocol) | データチャンネルの確立。ラベル等SCTPでは表現できない機能を補完 |
| **DTLS** | SCTPが動作する暗号化レイヤー |

SCTPは [RFC 4960](https://tools.ietf.org/html/rfc4960)、DCEPは [RFC 8832](https://tools.ietf.org/html/rfc8832) で定義されている。

---

## 3. DCEP（Data Channel Establishment Protocol）

2つのメッセージのみで構成されるシンプルなプロトコル。

| メッセージ | 役割 |
|-----------|------|
| **DATA_CHANNEL_OPEN** | チャンネルの開設を要求 |
| **DATA_CHANNEL_ACK** | チャンネル開設の確認応答 |

### DATA_CHANNEL_OPENの主要フィールド

| フィールド | 説明 |
|-----------|------|
| **Channel Type** | 信頼性・順序の属性を制御 |
| **Priority** | チャンネルの優先順位 |
| **Reliability Parameter** | 再送回数またはタイムアウト時間 |
| **Label** | チャンネル名（UTF-8文字列） |
| **Protocol** | サブプロトコル指定（WebSocket Subprotocol Registry準拠） |

### チャンネルタイプ一覧

| タイプ | 信頼性 | 順序 |
|--------|--------|------|
| `DATA_CHANNEL_RELIABLE` (`0x00`) | 損失なし | 順序あり |
| `DATA_CHANNEL_RELIABLE_UNORDERED` (`0x80`) | 損失なし | 順序なし |
| `DATA_CHANNEL_PARTIAL_RELIABLE_REXMIT` (`0x01`) | 再送回数上限あり | 順序あり |
| `DATA_CHANNEL_PARTIAL_RELIABLE_REXMIT_UNORDERED` (`0x81`) | 再送回数上限あり | 順序なし |
| `DATA_CHANNEL_PARTIAL_RELIABLE_TIMED` (`0x02`) | 時間上限あり | 順序あり |
| `DATA_CHANNEL_PARTIAL_RELIABLE_TIMED_UNORDERED` (`0x82`) | 時間上限あり | 順序なし |

## 4. SCTPの主要概念

### アソシエーション
- SCTPのセッション（接続状態）のこと
- 2つのSCTPエージェント間で共有される状態

### ストリーム
- ユーザーデータの双方向シーケンス
- データチャンネル = SCTPストリーム
- 各ストリームに異なる信頼性タイプを設定可能
- WebRTCではストリーム作成時にのみ設定変更可（SCTP自体はいつでも変更可能）

### データグラムベース
- バイトストリームではなく**データグラム**単位でフレーム化
- UDPを使っているような感覚で送受信
- UDPとは異なりサイズ制限なし（複数GBも可能）

### チャンク
- SCTPプロトコルの通信単位
- 1つのUDPパケットに複数チャンクを格納可能
- 異なるストリームのメッセージを1パケットで運搬

---

## 5. SCTPの主要チャンク

### DATAチャンク（Type=0）

ユーザーデータを運ぶチャンク。

| フィールド | 説明 |
|-----------|------|
| **U ビット** | 順不同フラグ。設定時はStream Sequence Numberを無視 |
| **B / E ビット** | フラグメント化の開始/終了ビット |
| **TSN** | Transmission Sequence Number。グローバルな一意識別子 |
| **Stream Identifier** | データが属するストリームの識別子 |
| **Stream Sequence Number** | メッセージ単位でインクリメント。順序配信に使用 |
| **PPID** | ペイロードプロトコル識別子 |

**フラグメント化の表現**:

| B | E | 意味 |
|---|---|------|
| 1 | 0 | フラグメントの最初 |
| 0 | 0 | フラグメントの中間 |
| 0 | 1 | フラグメントの最後 |
| 1 | 1 | フラグメント化なし（完全なメッセージ） |

**WebRTCで使用するPPID**:

| PPID | 用途 |
|------|------|
| `50` (WebRTC DCEP) | DCEPメッセージ |
| `51` (WebRTC String) | 文字列メッセージ |
| `53` (WebRTC Binary) | バイナリメッセージ |
| `56` (WebRTC String Empty) | 長さ0の文字列メッセージ |
| `57` (WebRTC Binary Empty) | 長さ0のバイナリメッセージ |

### INITチャンク（Type=1）

アソシエーション確立を開始するチャンク。

| フィールド | 説明 |
|-----------|------|
| **Initiate Tag** | クッキー生成に使用（MitM・DoS対策） |
| **a_rwnd** | 受信者のバッファサイズ（輻輳制御用） |
| **Outbound/Inbound Streams** | サポートするストリーム数 |
| **Initial TSN** | TSNの開始値（ランダムなuint32） |

### SACKチャンク（Type=3）

選択的確認応答。受信状況を送信者に通知する。

| フィールド | 説明 |
|-----------|------|
| **Cumulative TSN Ack** | 受信した最も高いTSN |
| **a_rwnd** | 受信者のバッファサイズ |
| **Gap Ack Blocks** | Cumulative TSN Ack以降に受信済みのTSN範囲 |
| **Duplicate TSNs** | 重複受信したTSN |

> Gap Ack Blocksにより、歯抜けで受信したパケットの不要な再送を防ぐ。例: TSN 100, 102, 103, 104を受信した場合、Cumulative TSN Ackは100だが、Gap Ack Blocksで102-104を通知することで再送を回避。

### HEARTBEATチャンク（Type=4）

- リモートの応答確認（生存確認）
- DATAチャンクを送信していないときのNATマッピング維持に有用

### ABORTチャンク（Type=6）

- アソシエーションの**異常終了**
- エラー状態で使用

### SHUTDOWNチャンク（Type=7）

- アソシエーションの**グレースフル終了**
- Cumulative TSN ACKで最後のTSNを通知し、全データの配信を保証
- WebRTCはSCTPアソシエーションのグレースフルシャットダウンを行わない（各データチャネルを個別に終了する必要がある）

### ERRORチャンク（Type=9）

- 致命的でないエラーの通知

### FORWARD TSNチャンク（Type=192）

- グローバルTSNを前方にスキップ
- パーシャル・リライアビリティで不要になったパケットを破棄するために使用
- 例: TSN 10-15を送信したが12, 13が欠落した場合、14, 15も無意味なのでFORWARD TSNでスキップ

## 6. ステートマシン

### 接続確立（4ウェイハンドシェイク）

```
クライアント                    サーバー
    |---- INIT -------------------->|
    |<--- INIT ACK (Cookie) --------|
    |---- COOKIE ECHO ------------->|
    |<--- COOKIE ACK ---------------|
    |      (DATAチャンク交換開始)     |
```

- **INIT / INIT ACK**: 各ピアの能力と構成を交換
- **クッキー**: MitM攻撃およびDoS攻撃の防止に使用
- **COOKIE ECHO / COOKIE ACK**: クッキー検証による接続確認

### コネクション・ティアダウン

- `SHUTDOWN`チャンクを使用
- 要求された`Cumulative TSN ACK`の受信を待つことで、接続にロスがあっても全データを確実に配信

### キープアライブ

- `HEARTBEAT REQUEST` / `HEARTBEAT ACK` を設定可能な間隔で送信
- パケット未到着時は**指数関数的バックオフ**を実施
- HEARTBEATに含まれる時間値でトリップタイムを計算

---

## 7. プロトコルスタック全体像

```
+---------------------------+
|      Data Channel API     |  ← アプリケーション
+---------------------------+
|          DCEP             |  ← チャンネル確立
+---------------------------+
|          SCTP             |  ← 多重化・信頼性・輻輳制御
+---------------------------+
|          DTLS             |  ← 暗号化
+---------------------------+
|          ICE/UDP          |  ← トランスポート
+---------------------------+
```

## まとめ

| テーマ | ポイント |
|--------|---------|
| データチャンネル | 最大65,534個。信頼性・順序を柔軟に設定可能 |
| DCEP | OPEN/ACKの2メッセージでチャンネル確立 |
| SCTP | データチャンネルの基盤。多重化・信頼性・輻輳制御・フロー制御を提供 |
| チャンク | DATA, INIT, SACK, HEARTBEAT, SHUTDOWN, FORWARD TSN等で通信 |
| 接続確立 | 4ウェイハンドシェイク（クッキーによるDoS/MitM防止） |
| パーシャル・リライアビリティ | FORWARD TSNで不要パケットをスキップし、リアルタイム性を確保 |

> データチャンネルはSCTPの上に構築され、TCPのような信頼性とUDPのような低遅延を柔軟に使い分けられる。DCEPでチャンネルを確立し、SCTPがデータの多重化・順序制御・輻輳回避を担うことで、メディア通信とは独立した汎用的なデータ通信を実現している。
