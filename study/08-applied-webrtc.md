# 08 WebRTCの応用

## 概要

WebRTCはブラウザでの会議だけでなく、様々なユースケースに利用されている。プロダクショングレードのWebRTCサービス構築には多くの課題がある。

## ユースケース別

| ユースケース | 概要 |
|------------|------|
| **会議** | WebRTCの最初のユースケース。輻輳制御、アダプティブビットレート、複数ストリーム対応 |
| **放送** | ブラウザで簡単に動画公開可能。遅延と品質のトレードオフを細かく制御できる |
| **リモートアクセス** | NATトラバーサルで固定IP不要。データチャネルでHead-of-lineブロッキングを回避 |
| **ファイル共有・検閲回避** | ブラウザで即利用可能。汎用プロトコルなのでブロックされにくい |
| **IoT** | P2Pでプライバシー向上。多言語対応で相互運用性が高い |
| **メディアプロトコルブリッジング** | SIPやRTSPなど既存プロトコルとの変換 |
| **データプロトコルブリッジング** | SSH等へのブラウザからのアクセス。信頼性の低い配信でレイテンシ改善 |
| **遠隔操作** | ロボット・車などの遠隔制御。データチャネル+RTPで実現 |
| **分散型CDN** | ユーザー間でファイル共有し、外部接続の負荷を軽減 |

## WebRTCトポロジー

### トポロジーとは

**トポロジー（Topology）** は、ネットワークにおける接続形態・構成のこと。WebRTCでは「複数の参加者をどのように接続するか」というネットワーク構成パターンを指す。

```
【1対1】          【フルメッシュ】        【SFU】
  A ─── B           A ─── B              A
                     \ × /                \
                      \ /              ┌───────┐
                       C               │ Server│
                                       └───────┘
                                        / | \
                                       B  C  D
```

### 各トポロジーの比較

| トポロジー | 接続方式 | メリット | デメリット |
|-----------|---------|---------|-----------|
| **1対1** | 直接接続 | シンプル | 2人限定 |
| **フルメッシュ** | 全員が全員と接続 | サーバー不要 | 人数増で帯域爆発 |
| **ハイブリッドメッシュ** | ピア経由でメディア中継 | 帯域節約 | レイテンシ増加 |
| **SFU** | サーバー経由で転送 | スケーラブル、1回のアップロードで全員に配信 | サーバーが必要 |
| **MCU** | サーバーで合成して配信 | クライアント負荷低 | サーバー負荷高 |

### なぜトポロジーが重要か

参加者が増えると、フルメッシュでは接続数が `n(n-1)/2` で増加する。例えば10人なら45接続必要。そのため、大規模な会議ではSFUやMCUのようなサーバー経由のトポロジーが使われる。
