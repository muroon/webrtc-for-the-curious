# 08 WebRTCの応用

## 概要

WebRTCはブラウザでの会議だけでなく、様々なユースケースに利用されている。プロダクショングレードのWebRTCサービス構築には多くの課題がある。

## ユースケース別

| ユースケース | 概要 |
|------------|------|
| **会議** | WebRTCの最初のユースケース。輻輳制御、アダプティブビットレート、複数ストリーム対応 |
| **放送** | ブラウザで簡単に動画公開可能。遅延と品質のトレードオフを細かく制御できる |
| **リモートアクセス** | NATトラバーサルで固定IP不要。データチャネルでHead-of-lineブロッキングを回避 |
| **ファイル共有・検閲回避** | ブラウザで即利用可能。汎用プロトコルなのでブロックされにくい |
| **IoT** | P2Pでプライバシー向上。多言語対応で相互運用性が高い |
| **メディアプロトコルブリッジング** | SIPやRTSPなど既存プロトコルとの変換 |
| **データプロトコルブリッジング** | SSH等へのブラウザからのアクセス。信頼性の低い配信でレイテンシ改善 |
| **遠隔操作** | ロボット・車などの遠隔制御。データチャネル+RTPで実現 |
| **分散型CDN** | ユーザー間でファイル共有し、外部接続の負荷を軽減 |

## WebRTCトポロジー

### トポロジーとは

**トポロジー（Topology）** は、ネットワークにおける接続形態・構成のこと。WebRTCでは「複数の参加者をどのように接続するか」というネットワーク構成パターンを指す。

```
【1対1】          【フルメッシュ】        【SFU】
  A ─── B           A ─── B              A
                     \ × /                \
                      \ /              ┌───────┐
                       C               │ Server│
                                       └───────┘
                                        / | \
                                       B  C  D
```

### 各トポロジーの比較

| トポロジー | 接続方式 | メリット | デメリット |
|-----------|---------|---------|-----------|
| **1対1** | 直接接続 | シンプル | 2人限定 |
| **フルメッシュ** | 全員が全員と接続 | サーバー不要 | 人数増で帯域爆発 |
| **ハイブリッドメッシュ** | ピア経由でメディア中継 | 帯域節約 | レイテンシ増加 |
| **SFU** | サーバー経由で転送 | スケーラブル、1回のアップロードで全員に配信 | サーバーが必要 |
| **MCU** | サーバーで合成して配信 | クライアント負荷低 | サーバー負荷高 |

### なぜトポロジーが重要か

参加者が増えると、フルメッシュでは接続数が `n(n-1)/2` で増加する。例えば10人なら45接続必要。そのため、大規模な会議ではSFUやMCUのようなサーバー経由のトポロジーが使われる。

## SFU（Selective Forwarding Unit）

### SFUとは

**SFU（選択的転送ユニット）** は、クライアント/サーバー型のトポロジーを実装したサーバー。フルメッシュの問題点を解決する。

```
┌─────────┐
│ User A  │──────┐
└─────────┘      │  アップロード
                 ▼
┌─────────┐   ┌─────┐   ┌─────────┐
│ User B  │◀─▶│ SFU │◀─▶│ User C  │
└─────────┘   └─────┘   └─────────┘
                 ▲
┌─────────┐      │
│ User D  │──────┘
└─────────┘

※ 各ユーザーは1回だけSFUにアップロード
※ SFUが全員に転送（フォワード）
```

### SFUの特徴

| 項目 | 説明 |
|------|------|
| **動作** | 各クライアントがSFUに接続し、メディアをアップロード。SFUが各クライアントに転送 |
| **エンコード** | サーバーでのエンコード/デコードは不要（パケットをそのまま転送） |
| **アップロード** | 各エージェントは1回だけエンコード・アップロード |
| **配信負担** | すべての視聴者への配信はSFUが担当 |

### SFUの利点

| 利点 | 説明 |
|------|------|
| **接続の簡素化** | ワールドルーティング可能なアドレスで動作可能 |
| **NATの問題軽減** | NATマッピングを気にする必要がない |
| **スケーラビリティ** | 参加者が増えてもクライアントの負荷は一定 |
| **帯域節約** | 各クライアントは1ストリームのみ送信 |

### SFUの注意点

- TCP経由で利用可能であることを確認する必要がある（ICE-TCPまたはTURN経由）
- シンプルなSFUは週末で構築可能
- 優れたSFUの構築（輻輳制御、エラー訂正、パフォーマンスチューニング）は終わりのない作業

## MCU（Multi-point Conferencing Unit）

### MCUとは

**MCU（多地点会議ユニット）** は、SFUと同様のクライアント/サーバー型トポロジーだが、出力ストリームを**合成**する点が異なる。

```
┌─────────┐
│ User A  │──────┐
└─────────┘      │
                 ▼
┌─────────┐   ┌─────┐   ┌─────────┐
│ User B  │◀─▶│ MCU │◀─▶│ User C  │
└─────────┘   └─────┘   └─────────┘
                 │
                 ▼
         ┌─────────────┐
         │ 合成された  │
         │ 映像を配信  │
         └─────────────┘
```

### SFUとMCUの比較

| 項目 | SFU | MCU |
|------|-----|-----|
| **サーバー処理** | パケット転送のみ | エンコード/デコード/合成 |
| **サーバー負荷** | 低い | 高い |
| **クライアント負荷** | 複数ストリームをデコード | 1ストリームのみデコード |
| **柔軟性** | 受信側で個別に画質調整可能 | 全員同じ映像を受信 |
| **スケーラビリティ** | 高い | サーバー性能に依存 |
