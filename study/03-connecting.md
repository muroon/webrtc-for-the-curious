# WebRTC接続の仕組み - NAT・STUN・TURN・ICE解説

この文書は、WebRTCにおけるNATマッピング、STUN、TURN、ICEについての質疑応答をまとめたものです。

---

## 1. NATマッピングの基礎

### マッピングとは

PCが `192.168.0.1:5000` から外部にパケットを送信すると、NATルーターが「マッピング」を作成します。

```
内部: 192.168.0.1:5000 → 外部: 203.0.113.10:30000
```

外部から見ると、PCは `203.0.113.10:30000` というアドレスになります。

---

## 2. マッピング作成の動作（送信時の振る舞い）

「別の宛先にパケットを送るとき、同じマッピングを再利用するか、新規作成するか」のルールです。

| タイプ | 動作 | 例 |
|--------|------|-----|
| **エンドポイントに依存しない** | どこに送っても同じマッピングを再利用 | `A:80` と `B:443` に送信 → 両方とも `203.0.113.10:30000` から送られる |
| **アドレスに依存する** | 宛先IPが変わると新規マッピング | `A:80` と `A:443` → 同じマッピング<br>`A:80` と `B:80` → 別々のマッピング |
| **アドレスとポートに依存する** | 宛先IP**または**ポートが変わると新規マッピング | `A:80` と `A:443` → 別々のマッピング |

---

## 3. マッピングフィルタリングの動作（受信時の振る舞い）

「作成されたマッピングに対して、誰からのパケットを受け入れるか」のルールです。

`A:5000` にパケットを送信して、マッピング `203.0.113.10:30000` が作られた場合：

| タイプ | 動作 |
|--------|------|
| **エンドポイントに依存しない** | 誰でも `203.0.113.10:30000` にパケットを送れる（`B` も `C` もOK） |
| **アドレスに依存する** | `A` からのみ受信可能（`A:5000` でも `A:6000` でもOK）。`B` からは無視 |
| **アドレスとポートに依存する** | `A:5000` からのみ受信可能。`A:5001` からも無視 |

### WebRTCへの影響

- **エンドポイントに依存しない**タイプが最も接続しやすい（STUNで取得したアドレスを誰とでも共有できる）
- **アドレスとポートに依存する**タイプは最も厳しく、直接接続が困難 → TURNが必要になることが多い

---

## 4. STUN（Session Traversal Utilities for NAT）

### STUNの価値

**一言で言うと**: NATの向こう側から自分がどう見えているかを教えてくれるサービス

### STUN以前の問題

PCが外部サーバーにパケットを送信すると、NATは自動的にマッピングを作成するが、PC自身は自分の外部アドレス（例: `203.0.113.10:30000`）を知る方法がなかった。

P2P通信をするには、相手に「ここにパケットを送って」と自分のアドレスを伝える必要があるが、それができなかった。

### STUNが解決すること

```
1. あなた → STUNサーバーに「Binding Request」を送信
   (この時点でNATマッピングが作成される)

2. STUNサーバーは「あなたからのパケットは 203.0.113.10:30000 から来ましたよ」
   と「Binding Response」で返答

3. あなたは初めて自分の外部アドレスを知る
```

外部アドレスがわかれば、それを相手に伝えてP2P接続が可能になる。

---

## 5. TURN（Traversal Using Relays around NAT）

### TURNとは

**一言で言うと**: P2P接続ができない場合に使う「中継サーバー」

STUNで外部アドレスがわかっても、NATの種類によっては直接通信できないケースがある。このとき、TURNサーバーが間に入って中継する。

```
あなた ←→ TURNサーバー ←→ 相手
```

### 仕組み（3ステップ）

1. **アロケーション作成**: TURNサーバーに接続し、中継用のアドレス（中継トランスポートアドレス）をもらう
2. **パーミッション設定**: 「この相手からの通信を許可する」とTURNサーバーに伝える
3. **中継開始**: 以降、すべての通信がTURNサーバー経由で転送される

### STUNとの違い

| | STUN | TURN |
|---|---|---|
| 役割 | 自分の外部アドレスを知る | トラフィックを中継する |
| 通信経路 | P2P（直接） | サーバー経由 |
| サーバー負荷 | 低い（最初だけ） | 高い（常時中継） |
| コスト | 低い | 高い |

### TURNの2つの形態

#### 形態1: 片方だけがTURNを使う（通常のケース）

```
あなた ←→ TURNサーバー ←→ 相手
  ↑                         ↑
TURNクライアント         直接通信
(中継が必要)            (中継不要)
```

#### 形態2: 双方がTURNを使う（特殊なケース）

```
あなた ←→ TURNサーバーA ←→ TURNサーバーB ←→ 相手
  ↑                                          ↑
TURNクライアント                        TURNクライアント
```

両方が厳しい企業ネットワークにいて、UDPがブロックされている場合などに使用。

## 6. 「NATが厳しい」とは

### 緩い（接続しやすい）

| マッピング作成 | フィルタリング |
|---------------|---------------|
| エンドポイントに依存しない | エンドポイントに依存しない |

**特徴**:
- どこに送っても同じ外部アドレスが使われる
- 誰からでもパケットを受け取れる

→ STUNで取得したアドレスを相手に渡せば、すぐに通信できる

### 厳しい（接続しにくい）

| マッピング作成 | フィルタリング |
|---------------|---------------|
| アドレスとポートに依存する | アドレスとポートに依存する |

**特徴**:
- 宛先ごとに別の外部アドレスが作られる
- 自分が送った相手（同じIP:Port）からしかパケットを受け取れない

### 厳しいと何が困るか

```
1. あなた → STUNサーバーに送信
   マッピング作成: 203.0.113.10:30000 (STUNサーバー宛て専用)

2. あなた:「私のアドレスは 203.0.113.10:30000 です」と相手に伝える

3. 相手 → 203.0.113.10:30000 にパケットを送信

4. NATルーター:「このマッピングはSTUNサーバー用だ。
   知らないやつからのパケットは捨てる」→ 破棄
```

STUNで知ったアドレスがSTUNサーバーとの通信専用になってしまい、他の相手との通信に使えない。だからTURNが必要。

### 現実世界での「厳しいNAT」

- 携帯キャリアのネットワーク（CGNAT）
- 企業のファイアウォール
- 一部の安価なルーター

## 7. ICE（Interactive Connectivity Establishment）

### ICEとは

**一言で言うと**: 2つのピア間で最適な通信経路を見つけるためのフレームワーク

ICEは「接続方法を探して試す仕組み」であり、STUNとTURNはその中で使われるツール。

### 関係性

```
┌─────────────────────────────────────┐
│               ICE                    │
│  (接続確立のフレームワーク)            │
│                                      │
│   ┌─────────┐      ┌─────────┐      │
│   │  STUN   │      │  TURN   │      │
│   │(アドレス │      │ (中継)   │      │
│   │  発見)  │      │         │      │
│   └─────────┘      └─────────┘      │
└─────────────────────────────────────┘
```

### ICEの流れ

#### 1. 候補（Candidate）の収集

| 候補の種類 | 取得方法 | 優先度 |
|-----------|---------|-------|
| Host | ローカルIPをそのまま使う | 高（最速） |
| Server Reflexive | **STUN**で外部アドレスを取得 | 中 |
| Relay | **TURN**で中継アドレスを取得 | 低（最終手段） |

#### 2. 候補の交換

シグナリング（SDPのやり取り）で、お互いの候補リストを交換。

```
あなたの候補:
- 192.168.0.1:5000 (Host)
- 203.0.113.10:30000 (Server Reflexive)
- 198.51.100.5:40000 (Relay)

相手の候補:
- 192.168.1.1:6000 (Host)
- 198.51.100.20:35000 (Server Reflexive)
- 203.0.113.50:45000 (Relay)
```

#### 3. 接続性チェック

すべての候補ペアを試して、実際に通信できるか確認。

#### 4. 最適なペアを選択

通信できたペアの中から、最も優先度が高いものを選ぶ。

**優先順位**: Host同士 > Server Reflexive > Relay（TURN）

### まとめ

| 役割 | 説明 |
|------|------|
| **ICE** | 候補を集めて、試して、最適な経路を選ぶ「司令塔」 |
| **STUN** | ICEが候補（Server Reflexive）を集めるために使う |
| **TURN** | 直接接続できない場合にICEが使う「最終手段」 |

## 8. ICEのユーザーフラグメントとパスワード

### 役割

| 名称 | 用途 |
|------|------|
| **ユーザーフラグメント (ufrag)** | 複数のICEセッションを識別するためのID（プレーンテキストで送信） |
| **パスワード (pwd)** | STUNパケットの認証・改ざん検出に使用 |

### 生成

WebRTCでは、ブラウザ（またはWebRTCライブラリ）が自動生成する。

```javascript
const pc = new RTCPeerConnection();
const offer = await pc.createOffer();
```

生成されたSDP（Session Description）の中に含まれる：

```
a=ice-ufrag:abcd1234
a=ice-pwd:asd88fgpdd777uzjYhagZg
```

### 交換（配布）

シグナリングを通じて相手と交換。

```
1. あなた: SDPを作成（ufrag/pwdが含まれる）
2. あなた → シグナリングサーバー → 相手: SDPを送信
3. 相手: SDPを受け取り、あなたのufrag/pwdを知る
4. 相手 → あなた: 同様に相手のufrag/pwdを受け取る
```

### 使われ方

接続性チェック（STUNパケット）で使用。

```
STUNパケット:
┌──────────────────────────┐
│ ヘッダー                  │
├──────────────────────────┤
│ USERNAME: 相手ufrag:自分ufrag │  ← セッション識別
├──────────────────────────┤
│ ...その他の属性...         │
├──────────────────────────┤
│ MESSAGE-INTEGRITY        │  ← パスワードでHMAC-SHA1
└──────────────────────────┘
```

- **USERNAME**: `相手のufrag:自分のufrag` の形式で、どのセッションかを識別
- **MESSAGE-INTEGRITY**: パスワードを鍵としてパケット全体をハッシュ化。改ざんされていないことを検証

### 保持

| 保持する側 | 保持期間 |
|-----------|---------|
| WebRTCスタック（ブラウザ等） | PeerConnectionが存在する間 |
| ICEエージェント | セッションが有効な間（またはICE再起動まで） |

ユーザーが直接生成・管理する必要はなく、WebRTCが自動で生成・交換・検証を行う。
