# メディア・コミュニケーション解説

この文書は、WebRTCにおけるメディア通信の仕組み（RTP/RTCP、動画圧縮、帯域幅推定）についてまとめたものです。

---

## 1. WebRTCメディア通信の概要

- オーディオ・ビデオのストリームを**無制限**に送受信可能
- 通話中にストリームの追加・削除が可能
- **コーデック非依存**（基礎トランスポートはすべてをサポート）
- 動的なネットワーク状況（帯域変動、パケットロス）に適応する設計

---

## 2. 使用プロトコル

| プロトコル | 役割 |
|-----------|------|
| **RTP** (Real-time Transport Protocol) | メディアデータの伝送。タイミング・順序情報を提供 |
| **RTCP** (RTP Control Protocol) | 通話のメタデータ通信。統計情報、パケットロス処理、輻輳制御 |

両プロトコルは [RFC 3550](https://tools.ietf.org/html/rfc3550#section-6.4) で定義されている。

---

## 3. レイテンシー vs クオリティ

- リアルタイムメディアは**遅延と品質のトレードオフ**
- 遅延を許容するほど高品質な映像が期待できる
- ネットワークの特性（帯域、パケットロス、ジッター等）が制約となる

---

## 4. 動画圧縮の基礎

### ロスレス vs ロッシー圧縮

| 種類 | 特徴 |
|------|------|
| **ロスレス** | 情報損失なし。データ量が多く遅延が大きい |
| **ロッシー** | 情報が失われる可能性あり。RTPでは一般的 |

### フレーム圧縮の種類

| 圧縮方式 | 説明 |
|---------|------|
| **イントラフレーム圧縮** | 1つのフレーム内でビットを削減（JPEG等） |
| **インターフレーム圧縮** | フレーム間の重複情報を排除 |

### フレームの種類

| フレーム | 説明 |
|---------|------|
| **I-Frame** | 完全な画像。単独でデコード可能 |
| **P-Frame** | 部分的な画像。前の画像を修正したもの |
| **B-Frame** | 部分的な画像。前後の画像を組み合わせたもの |

> 動画圧縮は非常に**ステートフル**であり、I-Frameの一部が失われるとP-Frameのデコードに影響する。RTPとRTCPにはこの問題への解決策がある。

---

## 5. RTPパケット構造

主要フィールド:

| フィールド | 説明 |
|-----------|------|
| **バージョン (V)** | 常に `2` |
| **パディング (P)** | ペイロードにパディングがあるか |
| **拡張 (X)** | ヘッダー拡張の有無 |
| **CSRC数 (CC)** | 貢献ソース識別子の数 |
| **マーカー (M)** | ユーザー定義（キーフレームや発話中の表示等） |
| **ペイロードタイプ (PT)** | コーデック識別子（WebRTCでは動的） |
| **シーケンス番号** | パケット順序付け。パケットロスの検出に使用 |
| **タイムスタンプ** | メディアストリーム内の経過時間 |
| **SSRC** | ストリームの一意識別子 |
| **CSRC** | どのSSRCがパケットに貢献したかのリスト |

## 6. RTCPメッセージタイプ

### FIR / PLI（キーフレーム要求）

| 種類 | 用途 |
|------|------|
| **FIR** (Full INTRA-frame Request) | パケットロス以外の理由でキーフレームを要求（例: 新規参加者） |
| **PLI** (Picture Loss Indication) | デコーダにパーシャルフレームが届きデコードできない場合 |

実際には両方とも同じ動作: エンコーダーに新しいフルキーフレームの生成を指示。

### NACK（否定確認応答）

- 送信者に特定のRTPパケットの再送を要求
- フレーム全体の再送より帯域効率が良い

### Sender Report / Receiver Report

エージェント間の統計情報を送信:

| フィールド | 説明 |
|-----------|------|
| **Fraction Lost** | 前回のRR以降のパケットロス率 |
| **Cumulative Packets Lost** | 通話全体の累積パケットロス数 |
| **Extended Highest Sequence Number** | 最後に受信したシーケンス番号 |
| **Interarrival Jitter** | 通話全体のローリングジッター |
| **Last Sender Report Timestamp** | RTT計算用の最後の送信者時間 |

**RTTの計算**:

```
rtt = sendertime2 - sendertime1 - DLSR
```

- 送信者がSRにローカル時刻 `sendertime1` を含める
- 受信者がRRに `sendertime1` と処理遅延 `DLSR` を含めて返す
- 送信者が現在時刻 `sendertime2` から差し引いてRTTを算出

## 7. パケットロスへの対処

| 方式 | 仕組み | 特徴 |
|------|--------|------|
| **NACK** | 特定パケット（シーケンス番号指定）の再送要求 | 帯域効率が良い。小さな欠落の補修向き。往復時間分の遅延あり |
| **PLI** | フルキーフレーム（I-Frame）の新規生成を要求 | 複数パケット欠落でデコード不能になった場合にデコード状態をリセット |
| **FEC** (前方誤り訂正) | 冗長データを事前に送信 | 低遅延だが帯域消費が多い |

**NACKとPLIの使い分け**:

- パケットが1つだけ欠落 → **NACK**でそのパケットだけ再送要求すれば復元可能
- 複数パケット欠落でフレームがデコード不能、または後続のP-Frameも連鎖的に壊れている → **PLI**でキーフレームを丸ごと要求してデコード状態をリセットする方が合理的

**NACK/PLI vs FECの使い分け**:

NACK/PLIは**事後対処（リアクティブ）**、FECは**事前対処（プロアクティブ）**という違いがある。

- NACK/PLI: パケットロス検知 → 送信側に要求 → 再送/キーフレーム生成。**往復時間（RTT）分の遅延**が発生
- FEC: あらかじめ冗長データを付加して送信。受信側が自力で復元。**再送の往復が不要で低遅延**

| 条件 | 適した方式 |
|------|-----------|
| RTTが大きい（遠距離通信等） | FEC（再送の往復を待てない） |
| RTTが小さい | NACK（再送で十分間に合う） |
| パケットロスが安定的に発生 | FEC（常時の冗長で吸収） |
| パケットロスがまれ | NACK（FECの帯域消費が無駄） |
| 帯域に余裕がない | NACK/PLI（FECの冗長分を割けない） |
| 超低遅延が必要 | FEC（往復を待つ余裕がない） |

実際のWebRTC実装では、これらを**併用**するのが一般的。FECで小さなロスを吸収しつつ、FECで復元できなかった場合にNACKで再送要求し、それでもデコードが破綻したらPLIでキーフレームを要求する多段構成となる。

## 8. 帯域幅推定と輻輳制御

### GCC (Google Congestion Control)

2つのコントローラで帯域を推定:

**ロスベース・コントローラ**:

| パケットロス率 | アクション |
|--------------|-----------|
| 10%超 | 推定帯域を縮小 |
| 2〜10% | 推定帯域を維持 |
| 2%以下 | 推定帯域を増加 |

**遅延ベース・コントローラ**:

- パケット到着間時間の変動を監視
- キューの深さ増加（＝輻輳の兆候）を**パケットロス発生前に**検出
- カルマンフィルターでジッターのノイズを除去し正確な予測を行う
- 輻輳を検出したらビットレートを下げ、安定時は徐々に増加

### TMMBR / TMMBN / REMB（受信側推定方式）

| プロトコル | 説明 |
|-----------|------|
| **TMMBR** | 1つのSSRCに対する要求ビットレート |
| **TMMBN** | TMMBRの受信確認 |
| **REMB** | セッション全体の要求ビットレート |

**問題点**: エンコーダの非効率性

- エンコーダが指定ビットレート通りに出力しない場合がある
- 受信側が低いビットレートをREMBで通知 → さらにビットレートが下がる悪循環
- 良好な接続でも映像品質が低下する可能性

### TWCC (Transport Wide Congestion Control)

最新の方式。受信側が各パケットの到着時刻を送信側に通知し、**送信側で帯域推定**を行う。

**メリット**:

- パケットロスの挙動をほぼ瞬時に把握（個々のパケット単位）
- 正確な送信/受信ビットレート
- ジッター測定
- 送信パケット遅延と受信パケット遅延の差分
- 輻輳制御アルゴリズムを送信側に集約 → クライアントコードがシンプル
- ブラウザ更新を待たずにアルゴリズム改善が可能

---

### 補足: GCCのドラフト名称について

元ドキュメントで言及されている `draft-alvestrand-rmcat-congestion`（"A Google Congestion Control Algorithm for Real-Time Communication"）と `draft-ietf-rmcat-gcc` は同じGCCアルゴリズムを指す。

| ドラフト | 段階 |
|---------|------|
| `draft-alvestrand-rmcat-congestion` | 初期の個人提出ドラフト（著者: Harald Alvestrand, Google） |
| `draft-ietf-rmcat-gcc` | IETF RMCATワーキンググループに採択された版 |

IETFの標準化プロセスにおいて、個人ドラフトがワーキンググループに採択されると名前が変わる。内容は同じ系統のドキュメント。GCCが最も多く導入されており、代替として NADA や SCReAM がある。

## 9. 帯域幅推定の世代比較

| 世代 | 方式 | 帯域推定の実行場所 | 特徴 |
|------|------|------------------|------|
| 第1世代 | SR/RR | 送信側 | 基本的な統計情報の交換 |
| 第2世代 | REMB | 受信側 | 受信側で推定して通知。エンコーダ非効率が問題 |
| 第3世代 | TWCC | 送信側 | 生データを送信側に提供。柔軟性が高い |

---

## まとめ

| テーマ | ポイント |
|--------|---------|
| プロトコル | RTP（メディア伝送）+ RTCP（メタデータ・制御） |
| 動画圧縮 | I/P/B-Frameによるインターフレーム圧縮。ステートフルで損失に弱い |
| パケットロス対策 | NACK（再送要求）、FEC（冗長データ） |
| キーフレーム要求 | FIR（新規参加者等）、PLI（デコード失敗時） |
| 輻輳制御 | GCC（ロスベース＋遅延ベース）が主流。TWCCが最新 |

> RTPでメディアを伝送し、RTCPでネットワーク状況を監視・フィードバックすることで、変動するネットワーク環境に適応的に対応する。帯域推定はGCC+TWCCの組み合わせが現在の主流であり、送信側でのアルゴリズム改善が容易な設計になっている。
