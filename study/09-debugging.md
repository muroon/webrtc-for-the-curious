# 09 デバッグ

## 概要

WebRTCのデバッグは非常に困難な作業。多くの可動部品があり、それぞれが独立して壊れる可能性がある。問題をどこで切り分けるかを理解し、適切なツールを使うことが重要。

## 問題の切り分け

| 問題の種類 | 概要 |
|-----------|------|
| **シグナリングの失敗** | SDPの交換やICE候補の送受信に関する問題 |
| **ネットワーキングの失敗** | STUN/TURNサーバーへの接続、NAT越えの問題 |
| **セキュリティの失敗** | DTLS/SRTPのハンドシェイク失敗 |
| **メディアの障害** | エンコード/デコード、パケットロスによる映像・音声の問題 |
| **データの障害** | DataChannelの接続・通信の問題 |

### STUNサーバーのテスト（netcat使用）

```bash
# 20バイトのバインディングリクエストを送信
stunserver=stun1.l.google.com;stunport=19302;listenport=20000
echo -ne "\x00\x01\x00\x00\x21\x12\xA4\x42TESTTESTTEST" | nc -u -p $listenport $stunserver $stunport -w 1 | hexdump -C
```

レスポンスの構造：
- `00 01` / `01 01` - メッセージタイプ（リクエスト/レスポンス）
- `21 12 a4 42` - マジッククッキー
- 12バイト - トランザクションID
- `00 20` - xor-mapped-address属性

## デバッグツール

| ツール | 用途 |
|-------|------|
| **netcat (nc)** | TCP/UDPネットワーク接続の読み書き |
| **tcpdump** | コマンドラインパケットキャプチャ。PCAPファイル出力可能 |
| **Wireshark** | GUIプロトコルアナライザ |
| **webrtc-internals** | Chrome内蔵の統計ページ（`chrome://webrtc-internals`） |

### tcpdumpの使用例

```bash
# UDPポート19302のパケットをキャプチャ（16進数表示）
sudo tcpdump 'udp port 19302' -xx

# PCAPファイルに保存
sudo tcpdump 'udp port 19302' -w stun.pcap
```

## レイテンシー測定

### エンドツーエンドレイテンシーとは

カメラキャプチャ → エンコード → 送信 → 受信 → デコード → 表示 までの全体の遅延時間。各コンポーネントの遅延の単純な合計ではなく、キューイングやネットワーク状態で変動する。

### 手動測定方法

```
EndToEndLatency = T(observe) - T(happen)
```

1. ミリ秒タイマーにカメラを向ける
2. 同じ場所の受信機にビデオフレームを送信
3. タイマーと受信映像を同時に撮影（携帯電話使用）
4. 2つの時間を引き算

→ クロック同期不要で最も正確な方法

### 自動測定方法（NTPスタイル）

DataChannelを使ったラウンドトリップ測定：

1. 受信者が時刻 `tR1` を送信者に送信
2. 送信者が `tR1` + 自分の時刻 `tS1` + ビデオトラック時間 `tSV1` を返信
3. 受信者が `tR2` で受信し、RTT = `tR2 - tR1` を計算
4. 送信者のクロックを推定：`tS1 + RTT/2`
5. 期待されるビデオ時間と実際のビデオ時間の差がレイテンシー

```javascript
// ブラウザでの実際のビデオ時間取得
VIDEO.requestVideoFrameCallback((now, framemeta) => {
    let actualVideoTimeMsec = Math.trunc(framemeta.rtpTimestamp / 90);
    // レイテンシー計算...
});
```

## レイテンシーデバッグのヒント

### カメラのレイテンシー

| 設定 | 影響 |
|-----|------|
| 自動露出 | 画像分析に時間がかかる |
| 自動フォーカス | 画像分析に時間がかかる |
| 自動ホワイトバランス | 画像分析に時間がかかる |

```bash
# Linuxでの設定（v4l2-ctl）
v4l2-ctl -d /dev/video0 -c focus_auto=0      # オートフォーカス無効化
v4l2-ctl -d /dev/video0 -c focus_absolute=0  # フォーカスを無限大に
```

### エンコーダーのレイテンシー

- 過剰な参照フレームやBフレームを避ける
- x264の場合：`tune=zerolatency`、`profile=baseline` を使用

### ネットワークのレイテンシー

| 指標 | 説明 |
|-----|------|
| **RTT（ラウンドトリップタイム）** | パケットの往復時間。レイテンシーの下限は RTT/2 |
| **パケットロス** | UDPは配送保証なし。ロスがあるとデコードアーティファクト発生 |
| **NACK** | 受信者が紛失パケットの再送を要求。再送待ちでレイテンシー増加 |
| **PLI** | 受信者がIフレーム再生成を要求。Iフレームはサイズが大きく遅延増加 |

webrtc-internalsで `nackCount`、`pliCount` を監視し、増加している場合はネットワーク品質に問題あり。

### 受信側のレイテンシー

- パケットが順不同で到着するとジッターバッファで待機が発生
- `jitterBufferDelay` で待機時間を確認可能
